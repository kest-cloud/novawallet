## 💬 2. Real Prompts Used During Development

### Prompt 1: Standalone Offline Action Queue & Sync Engine
> *"In `lib/core/sync/`, build a persisted offline action queue as a standalone, feature-agnostic service.*
> *Requirements:*
> *- `QueuedAction` entity: id, idempotencyKey (generated via uuid), actionType (enum), payload (Map<String, dynamic> — kobo values as int), status (pending/sending/sent/failed), createdAt.*
> *- Persist using sqflite — NOT SharedPreferences. Must survive app kill and restart.*
> *- SyncQueueRepository interface in domain, sqflite-backed implementation in data.*
> *- A SyncEngine that: listens to connectivity changes, on reconnect processes the queue FIFO, marks each entry 'sending' BEFORE the network call, and marks 'sent' (removing it) only after a successful response.*
> *- On app startup, the SyncEngine must treat any entry already in 'sending' state the same as 'pending' and resume it — this is the case that guarantees exactly-once even if the app was killed mid-replay.*
> *- Expose a stream/notifier so UI can show 'Pending — will send when back online' per action."*

### Prompt 2: Send Money Feature with Idempotency Guard
> *"Build `features/send_money/`, wired to the SyncEngine and SyncQueueRepository from `core/sync`.*
> *- Recipient → amount → confirm flow, three steps in one flow (stepper or PageView), all amounts entered/displayed as Money.*
> *- On confirm: generate ONE idempotency key for this attempt, enqueue a SendMoney QueuedAction via the core sync engine — do not implement a second, separate offline mechanism here.*
> *- If the device is offline at confirm time, show 'Pending — will send when back online' immediately instead of a spinner or error.*
> *- Guard against generating a new idempotency key on widget rebuild — it must be created once per user-initiated attempt, not once per build.*
> *Write a widget test that: drives the full recipient→amount→confirm flow, and asserts exactly one idempotency key is generated for one tap of Confirm (rebuild the widget tree once mid-flow to catch a key regenerated by build())."*

### Prompt 3: Quality Pass, Security Audit & App Integration Test
> *"Final pass across the whole app:*
> *1. Audit every place a token or credential is mocked/stored — confirm it goes through core/storage's secure storage wrapper, never SharedPreferences directly. Add a test that fails if SharedPreferences is used for anything containing 'token' or 'key' in its name.*
> *2. Full accessibility sweep: run through wallet_home, send_money, and nova_save with TalkBack/VoiceOver-style semantics tree inspection (semantics debugger in Flutter), fix any unlabeled interactive element.*
> *3. Font-scale sweep at 1.3x and 2.0x across all three screens — no clipped text, no broken layout.*
> *4. Write the top-level integration test explicitly required by the brief: offline → app restart → reconnect → exactly-once sync, at the app level (not just within core/sync), covering a real Send Money action.*
> *5. Write README.md and AI_USAGE.md."*

## 🔍 3. Three Case Scenarios Where AI Made Mistakes & How They Were Corrected

The following three scenarios represent actual technical mistakes and architectural risks introduced by AI generation during the project lifecycle and how they were caught and rectified.

---


### ❌ Case Scenario 1: Naive Double-Based Kobo↔Naira Conversion
- **Locations in Code**:
  - `lib/core/money/money.dart` (formatting logic)
  - `lib/features/nova_save/presentation/widgets/goal_progress_bar.dart` (progress percentage calculation)
- **The AI's Mistake & Technical Rationale**:
  When generating the `Money` value object's display formatter and the NovaSave progress calculation, the AI produced:
```dart
  // ❌ RISKY CODE GENERATED BY AI:
  String formatToNaira(int kobo) {
    double naira = kobo / 100; // implicit int-to-double division
    return '₦${naira.toStringAsFixed(2)}';
  }

  double getProgressPercent(int contributedKobo, int targetKobo) {
    return (contributedKobo / targetKobo) * 100; // double division
  }
```
  Both functions convert integer kobo into `double` before doing arithmetic. Dart's `/` operator on two `int`s returns a `double`, and repeated double arithmetic (especially across many small contributions) accumulates binary floating-point rounding error — the exact failure mode the brief explicitly warns about.
- **The Risk**:
  For most individual conversions the error is invisible (`naira.toStringAsFixed(2)` often hides it), but it compounds: a NovaSave goal receiving many small contributions can drift its displayed progress percentage away from the true integer ratio over time, and any future arithmetic done on the `double` result (rather than re-deriving it from kobo) permanently loses precision. In a financial app this is the class of bug that erodes trust even when it looks fine in a demo.
- **How It Was Caught**:
  While reviewing the `Money` and progress-calculation code against the brief's hard constraint that money must never touch a float, I flagged both functions before they were wired into the UI — the `int / int` division producing a `double` was the tell.
- **How It Was Corrected**:
  1. `formatToNaira` was rewritten to do integer division and remainder separately, only building the display string from integers:
```dart
     // ✅ INTEGER-SAFE FORMATTING:
     String formatToNaira(int kobo) {
       final naira = kobo ~/ 100;
       final remainder = (kobo % 100).abs();
       return '₦$naira.${remainder.toString().padLeft(2, '0')}';
     }
```
  2. `getProgressPercent` was changed to return an `int` (0–100) using integer math, with any further precision needed for the progress bar's fractional fill computed only inside the widget layer, never stored or compared as a `double`:
```dart
     // ✅ INTEGER-SAFE PROGRESS:
     int getProgressPercent(int contributedKobo, int targetKobo) {
       if (targetKobo == 0) return 0;
       return ((contributedKobo * 100) ~/ targetKobo).clamp(0, 100);
     }
```

### ❌ Case Scenario 2: Lazy Service Registration Breaking Sync Replay on App Cold Restart
- **The AI's Mistake**:
  In `lib/core/di/injection_container.dart`, the AI registered `TransferRepository` and `SavingsRepository` as `sl.registerLazySingleton<TransferRepository>(...)`.
  In the repository constructors, the repositories register their feature handlers (`ActionType.sendMoney` and `ActionType.contributeToGoal`) with `SyncEngine`.

  However, on app startup, `di.initDependencies()` executed `SyncEngine.init()`, which immediately read the SQLite database and attempted to replay pending actions before any UI screen requested `sl<TransferRepository>()`.
  
- **The Risk**:
  Because `TransferRepository` was lazily registered, its constructor had not yet run when `SyncEngine.init()` replayed the queue on startup. As a result, `SyncEngine` found no registered handler for `ActionType.sendMoney`, causing offline replays to fail silently or be skipped upon cold app restart.
- **How It Was Caught**:
  While reviewing `injection_container.dart` against the startup sequence in `main.dart`, I traced through the order of execution by hand — lazy singletons only construct on first access, but `SyncEngine.init()` ran before anything touched `sl<TransferRepository>()`. That ordering gap was visible from reading the registration and startup code side by side, before it ever needed a failing run to surface.
- **How It Was Corrected**:
  I updated `lib/core/di/injection_container.dart` to eagerly resolve `sl<TransferRepository>()` and `sl<SavingsRepository>()` immediately prior to calling `await sl<SyncEngine>().init()`, so handler registration is deterministic regardless of what the UI has or hasn't requested yet.

### ❌ Case Scenario 3: `DropdownButtonFormField` Overflow at 2.0x Accessibility Font Scale
- **The AI's Mistake**:
  In `SendMoneyScreen` (Step 1: Recipient Bank Selection), the AI placed a standard `DropdownButtonFormField<String>` inside the form without setting `isExpanded: true`. Additionally, in `NovaSaveScreen`, the savings vault header and target amounts were laid out inside standard rigid horizontal `Row` widgets.
- **The Risk**:
  While the layouts rendered without errors at standard 1.0x font scaling, users with visual impairments using TalkBack/VoiceOver with font scaling set to 1.3x or 2.0x encountered a severe layout breakdown:
  `A RenderFlex overflowed by 329 pixels on the right.`
  The bank selector and savings vault headers clipped and threw unhandled Flutter rendering exceptions.
- **How It Was Caught**:
  Caught by the automated accessibility and font scaling test suite (`test/core/accessibility/font_scale_and_semantics_sweep_test.dart`), which systematically pumps each screen wrapped with `MediaQuery(data: MediaQueryData(textScaler: TextScaler.linear(2.0)), ...)`.
- **How It Was Corrected**:
  1. In `SendMoneyScreen`, `isExpanded: true` was added to `DropdownButtonFormField<String>`.
  2. In `NovaSaveScreen`, rigid `Row` widgets were replaced with responsive `Wrap` widgets (`spacing: 8`, `runSpacing: 4`) and `FittedBox` widgets, ensuring all elements wrap cleanly on smaller viewports and large font sizes without `RenderFlex` exceptions.

## 📊 Summary of AI Collaboration Takeaways

1. **Automated Audits Catch Subconscious AI Shortcuts**: Automated tests (e.g., regex/AST checks preventing `SharedPreferences` token storage) ensure AI-generated code strictly adheres to security rules.
2. **Top-Level Integration Tests are Essential for Asynchronous Sync**: Micro unit tests often pass because mocks are explicitly wired in memory; only full end-to-end integration tests (like simulating app death and restart) catch subtle DI lifecycle race conditions.
3. **Accessibility is Non-Negotiable**: AI defaults often forget multi-scale accessibility constraints; automated font scaling sweeps (1.0x, 1.3x, 2.0x) should always be part of the continuous verification pipeline.
